信息供给层速查卡

先分清信息属于哪一层，再决定怎样保存、检索、核对与授权。任何一层都不能替代真实代码、测试与 Runtime 的执行门禁。

六类信息放在哪里

层回答的问题必须保留不能证明
Context Packing本轮给模型什么当前规则、约束、相关证据、预算外部动作已完成
Working Memory当前任务做到哪里目标、约束、风险、进度、未决项、事实引用现场仍未变化
Checkpoint中断前已记录什么状态、计划、证据、审批、计数、版本中断期间的真实副作用
Long-term Memory以后任务可复用什么项目知识、来源、范围、检查时间、失效条件当前源码仍然如此
RAG当前问题需要哪些外部证据来源、版本、片段、权限、检索过程回答已被证据支持
LLM Wiki多来源关系如何持续维护来源快照、草稿、依赖、发布记录、状态模型草稿就是事实

证据信封

Evidence = 内容摘要 + source + location + artifactVersion + executionId + observedAt + accessPolicy

结论要能回到具体来源与位置；代码或规则变化后，旧证据仍是历史事实，但未必能为当前状态背书。

RAG 排障顺序

  1. 正确来源是否已读取、解析、分块并带元数据入库？
  2. 正确证据是否进入候选集合？没有，先改数据准备或召回。
  3. 正确证据是否进入最终 Context？没有，检查过滤、重排、预算和压缩。
  4. 模型是否忠于最终证据？没有，要求引用、做结论支持校验或明确“不足以确认”。

知识更新的原子流程

授权快照 → 草稿(staging) → 结构/内容核验 → 再核对来源、权限、页版本 → 原子发布 → 索引/缓存/依赖同步

来源变更时，先用依赖图找受影响页面并标为待复核；不能全局替换旧数值，更不能把需求、建议或历史记录写成已上线事实。

交付前检查

  • 本轮 Context 是否保留必要约束与当前版本证据？
  • 记忆是否说明来源、适用范围、性质（要求/事实/推断）与失效条件？
  • RAG 回答的每条关键结论是否被对应证据支持，而非仅有合法编号？
  • 读取、生成、发布、检索、导出和缓存是否都执行访问控制？
  • 资料、记忆与源码冲突时，是否指出冲突并用当前代码/测试核验，而非擅自选一方？
