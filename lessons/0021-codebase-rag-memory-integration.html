Codebase RAG & Memory：让 Agent 看得见，也记得准

长期记忆解决跨 Run 遗忘；RAG 解决当前改代码前看不到业务依据。两者只提供可核对线索，不替代代码、测试、Runtime 和完成契约。

信息供给的正确连接

新任务 → Working Memory/Checkpoint 恢复当前状态
→ 检索 Long-term Memory + RAG 证据 → Context Packing
→ Loop/Runtime 执行 → 代码与测试产生新事实 → 更新记忆或知识库

例如 Agent 要修改 Spring Session 过期逻辑：RAG 提供业务规则与来源；长期记忆提供模块位置和 Maven 测试入口；源码与真实测试确认当前行为。三者冲突时，应指出冲突并用当前代码、测试与权威规则核验，不能静默选择看起来更可信的一方。

Memory 与 RAG 都是受治理能力

能力风险与边界必要验收
memory_recall读取跨会话知识，受项目/权限/范围过滤相关查询能取回；路径穿越和越权被拒
memory_remember写入项目知识，不能保存凭证或把推断当事实格式、来源、索引和日志同步；写入经审批/审计
rag_query只读检索，不修改知识库或工作区答案与编号来源一一对应；证据不足明确说明

三种能力均注册进 Tool Registry，经 RBAC、白名单、Runtime 和审计；模型不能直连文件、向量库或记忆目录。

五项端到端验收

  1. 找得到：RAG 能找回问题所需来源，且引用可定位。
  2. 装得下：装配器在预算内保留约束、当前状态和关键证据。
  3. 记得准：跨会话确实读取持久知识，而非恰好在聊天历史里出现。
  4. 恢复得了：中断后先核对现场，未把旧状态或旧授权当作当前事实。
  5. 解释得清：能说明使用了哪些资料、版本、工具结果与验证证据。

遇到资料与代码打架

RAG 查到“会话 30 分钟”，而当前源码实现为 20 分钟时，不能擅自称其中一方为真。回答应显式区分“资料规则/资料版本”和“源码观察/代码版本”，必要时运行受控测试或请求负责人裁决；资料更新与记忆更新也不能宣称代码已同步。

2. memory_remember 应走治理层还是直连存储？
