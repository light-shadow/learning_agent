从模型 API 到受控 Harness

模型 API 是概率生成接口；Harness 的工作，是让输入、输出、失败和供应商切换成为可验证工程能力。

先建立正确心智模型

传统 HTTP 请求通常有确定响应；模型请求由指令、上下文、参数共同塑造候选输出。工程师仍须定义任务目标、上下文、输出契约、权限/预算和失败边界。模型产生候选，系统决定怎样让候选可用。

API 与上下文

概念正确用法
Chat Completions以 messages 为中心，适合多供应商的稳定兼容基线。
Responses以输出项为中心；message、function_call、reasoning、refusal 等项是系统下一步的依据，不能只当文本。
rolessystem 是全局契约，user 是用户目标，assistant 是既有决策，tool 是外部观察。保留来源与顺序，才能裁剪、审计和重放。
context budgetsystem、输入、历史、工具结果和预留输出必须装进窗口。输入越长并不自动增加输出空间；长日志不能挤掉任务目标。

参数、契约与失败

temperature 控制随机性，top_p 是另一采样控制，实验一次只改变一个；max_tokens 是输出预算，finish_reason=length 的结构化结果应视为不完整失败。自然语言不能直接驱动程序：用 JSON 约束、Pydantic Schema 和业务规则三层防线。认证/本地参数错误不重试；网络、429、5xx 才能在最大次数、指数退避和 jitter 内重试；拒答、截断、格式错要按原因恢复或停止。

Adapter 边界

Loop 只依赖能返回文本、结构化结果或工具请求的能力协议；Provider Adapter 吸收 SDK、地址、模型名和供应商响应差异。这样切换模型等于替换构造对象，而不是污染 Loop。
