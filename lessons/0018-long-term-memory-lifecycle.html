Long-term Memory：保存可复用知识，而非保存一切

工作记忆帮助完成这一次 Run；长期记忆让下一次任务少走弯路，但它必须有来源、范围和失效策略。

先决定什么值得记

适合跨任务保存不应默认保存
模块位置、测试入口、稳定项目规则、已核验的故障经验当前补丁状态、一次性日志、猜测、凭证、令牌、完整用户载荷
“`OrderService` 由哪些测试覆盖”“我准备在下一轮修改哪个方法”

每条候选都问三件事：以后哪类任务会使用？来源能否核对？在什么条件下失效？

记录事实的“性质”

Knowledge Item = 内容 + 类型(要求/事实/推断) + project/scope + source + checkedAt + version/hash + expiry/status

“产品规则要求会话到期失效”“当前源码使用某比较符”“模型推测缓存相关”不是同一类知识。前者要看谁有权提出，后者要看证据是否仍适用于当前代码，推断只能作后续调查线索。

OKF 是可读知识包，不是事实担保

OKF 用 Markdown 正文、YAML 元数据、`index.md` 与 `log.md` 组织项目知识。格式校验只能检查结构，不能证明 `description` 中的模块位置仍然正确。模型在新会话应先检索相关候选、读取全文与来源，再检查当前代码。

冲突、失效与治理

更新或删除前先确认项目、范围与精确记录 ID。新消息更晚不代表更可靠，也可能针对另一分支。过期知识应退出默认当前查询，但若有历史价值可保留并标明范围；删除用于错误或不该保留的内容。记忆的 `remember`/`recall` 也是受治理工具：写入需权限、来源与审计，不能绕过 Runtime。

1. 新任务检索到旧测试命令后，应直接使用还是先核对？

2. 有历史价值但已过期的故障经验，应保留还是删除？
