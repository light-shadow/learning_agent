Agent Harness：把一次代码修改做完整

Harness 是顶层编排，不是又一个工具或 Loop：它让准备、修改、验证、异常、恢复、审批与交付在一条真实调用链上共同生效。

Context → Loop ↔ Runtime → Evidence / State / Checkpoint → Completion Contract → 交付；Governance 与 Sandbox 横切全链

为什么“模块正确”仍不够

模块Harness 要验证的真实连接
Context首轮只给任务、仓库摘要、相关片段、规则与工具；后续轮给当前状态、Tool Result、证据和缺项，历史不被错误污染。
Runtime / Loop每个 Tool Call 和 Result 用原 ID 关联；真实错误与完成缺项回灌下一轮；循环上限的模型 stop_reason 不冒充业务完成。
Evidence / Contract测试必须对应当前受测代码版本；代码再改，旧通过记录不能证明当前正确。完成还核对最终 Diff、范围、交付物和未执行限制。
异常与恢复先判动作未发生、已发生还是未知；未知先核查。恢复前重检工作区、版本、审批与外部状态。
变更审批先查询真实对象，暂存变更、展示、宿主批准后才执行；模型提交 ID 不等于可信对象，批准不跨动作复用。

端到端的两层验收

看决定：拒绝、取消、恢复、完成契约和 Follow-up 是否在正确 Hook 生效。看实际后果：文件是否修改、进程是否停止、测试是否在当前版本执行、批准前 handler 是否为 0。定位故障要找第一处断开的连接，而不是先改 Prompt。

可替换模型循环，不可替换业务事实

pi Loop 或自行实现的 Messages Loop 可以更换，但业务核心的 gates、executor、变更账本和统一 ToolOutcome 应复用；模型文本、UI 事件与审计均来自同一 Outcome，避免一边显示成功一边记录失败。
