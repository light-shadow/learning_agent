证明 Planning 真正可交付

本课胜利条件：你能用三层验证说明“计划不是提示词，而是正在生效的执行机制”。

不要混淆三件事：单测证明规则；集成测试证明接线；真实运行证明实际环境中的闭环。任何一层通过，都不能自动替代另两层。课程讲义 P29-P32

第一层：PlanStore 的确定性规则测试

这层不需要真实模型。直接构造计划、证据和修订请求，验证规则在边界处拒绝错误状态。

反例期望结果它证明什么
依赖未完成就 startPLAN_STEP_NOT_READY就绪性由程序计算，不由模型宣称。
无证据申请 completePLAN_COMPLETION_REQUIRES_EVIDENCE模型自述不能改变状态。
引用其他步骤证据PLAN_EVIDENCE_STEP_MISMATCH证据归属可追溯。
引用修改前测试结果PLAN_EVIDENCE_STALE交付证明必须对齐当前版本。
修订产生环PLAN_DEPENDENCY_CYCLE，快照不变修订是原子提交，不留下半成品状态。

第二层：Loop 集成测试

PlanStore 单测即使全绿，也不能证明它真的接在执行入口。这里要观察“被拒动作未触达 Runtime”。

缺少 planStepId
→ beforeToolCall 返回错误 Tool Result
→ Runtime handler 调用次数 = 0

绑定未就绪步骤
→ beforeToolCall 返回 PLAN_STEP_NOT_READY
→ Runtime handler 调用次数 = 0

还要测试模型提前输出 Final：当 Completion Contract 缺少目标、边界或回归证据时，系统必须注入 Follow-up 继续，而非结束任务。

第三层：真实运行留证据

真实运行回答的是“真实模型面对真实仓库和工具时，这条链路是否形成闭环”。它至少应记录：

  1. 运行的实际命令、退出码与测试范围。
  2. 代码版本变化和受控 diff。
  3. 计划步骤状态、计划修订记录与每步 Evidence 摘要。
  4. 交付说明实际落盘，以及已验证与未验证项。

真实运行不能用来替代所有边界单测；反过来，脚本测试也不能证明 Hook 在真实 Agent Loop 中没有被绕开。

完成契约的最终检查

可交付 = 当前版本有允许的改动
AND target / boundary / regression 证据均通过
AND 交付文档存在并说明未验证项
AND 任务未因取消、预算或权限限制停止

若环境缺少依赖、无法运行某组回归测试，正确结论是“部分验证、具体阻塞原因”，不是“完成”。

面试收口

“我把 Planning 的验收分为三层：
第一层用确定性测试验证状态、证据和修订规则；
第二层验证 beforeToolCall 真能拦住动作、afterToolCall 真能关联证据、Final 不足真能继续；
第三层通过真实任务确认代码、测试、计划记录和交付产物形成闭环。
这样我能区分已实现、已验证与未验证。”

检索练习：选择正确结论

1. PlanStore 的所有单测均通过，能否据此证明 Planning 整体可交付？

2. revise_plan 应用后发现依赖图有环，当前 Plan 应当？

3. 真实运行因缺少测试依赖而无法执行回归测试，应当？

本节收束

可靠的 Planning 不靠“模型看起来很有条理”，而靠错误动作被拦截、证据能复核、修订能回滚、真实运行可追溯。
