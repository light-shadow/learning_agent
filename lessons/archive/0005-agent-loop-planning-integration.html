Lesson 0005 · 约 15 分钟

把计划接进 Agent Loop，不再造第二套执行器

本课胜利条件：你能指出计划层的四个 Hook，并解释为什么 Tool Result、取消和最大轮数必须仍由原 Agent Loop 管理。

接线原则：Planning 是给既有 Agent Loop 加任务状态与验收门禁，不是额外复制一套“模型调用 → 工具执行 → 结果回写”的循环。课程讲义 P24-P28

一轮完整的计划化 Loop

Turn 开始
→ prepareNextTurn：注入 Plan 快照（版本 / 就绪步骤 / 最近证据）
→ 模型返回 Tool Call
→ beforeToolCall：planStepId 存在？步骤就绪？工具允许？
拒绝 → 错误 Tool Result 回写，handler = 0
通过 → 剥离 planStepId，调用 Runtime
→ afterToolCall：补全证据元数据，写入 EvidenceStore
→ 原 Tool Result 回写给模型
→ shouldStopAfterTurn：Completion Contract 是否通过？
否 → Follow-up 继续；是 → COMPLETED

四个 Hook 分工

Hook计划层新增行为一个常见错误
prepareNextTurn刷新当前快照，告诉模型现在能做什么。把每轮完整计划历史都追加到上下文，造成膨胀和过期信息。
beforeToolCall验证 planStepId 与依赖；通过后剥离编排字段。先执行 Runtime，再事后发现依赖不满足。
afterToolCall把真实结果关联到步骤、工具调用和代码版本。让模型用自然语言“登记证据”。
shouldStopAfterTurn由 Completion Contract 判断交付，而不是看模型是否输出 Final。模型沉默或说完成，就直接结束。

最小接线伪代码

prepareNextTurn(context) {
context.add(planStore.snapshot());
}

beforeToolCall(call) {
if (requiresPlanStep(call.name)) {
String id = requirePlanStepId(call);
planStore.assertExecutable(id);
call.removeArgument("planStepId");
}
}

afterToolCall(call, result) {
evidenceStore.append(toEvidence(call, result, currentCodeVersion));
}

shouldStopAfterTurn() {
return completionContract.verify(currentContext);
}

两条不能被计划层破坏的边界

原始 Tool Result

仍须写回模型

计划快照只是状态摘要，不能替换命令输出、测试日志和错误信息，否则模型失去排障所需事实。

真实停止原因

不能伪装完成

取消、预算耗尽、权限拒绝和阻塞必须如实输出；完成契约不通过时继续或报告，而非标记 COMPLETED。

如何证明“接线真的生效”？

只测 PlanStore 规则还不够。还要做 Loop 集成测试，观测边界行为：

  1. 受约束工具缺少 planStepId：handler 调用次数必须为 0。
  2. 绑定未就绪步骤：handler 调用次数必须为 0。
  3. 模型输出 Final，但目标/边界/回归证据不齐：系统注入 Follow-up 继续，不能停止。
  4. 完整闭环：Plan 版本变更、证据归属正确、源码真的被改、交付文档真的存在。

更多验收项见 Agent Loop 计划接线检查清单。

面试表达

“我不在 Planning 层新建第二个 Agent Loop。
我在原 Loop 的四个 Hook 接入：每轮注入快照、调用前门禁、调用后写证据、停止前验收。
原 Tool Result、取消、最大轮数和权限仍由原 Loop 管理，因此计划层不会绕过既有安全与可靠性机制。”

检索练习：判断接线行为

1. 模型输出 Final，但 Completion Contract 发现回归测试证据缺失，应当？

2. afterToolCall 写入 Evidence 后，模型下一轮仍应收到什么？

3. 任务在完成契约通过前耗尽轮数预算，应当？

带走的一句话

用 PlanStore 管任务状态，用 Runtime 产真实事实，用原 Agent Loop 保留执行控制；三者各自负责，不能相互替代。
