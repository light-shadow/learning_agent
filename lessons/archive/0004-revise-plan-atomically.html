Lesson 0004 · 约 15 分钟

revise_plan：计划可以改，验收标准不能降

本课胜利条件：你能区分局部纠错与计划修订，并说明为什么修订必须带版本、证据和原子提交。

先分流，再改动：工具失败不自动等于计划错。先判断是参数错误、暂时性故障、前提被推翻，还是权限/预算限制；只有路径或约束真正变化时，才修订计划。课程讲义 P19-P23

四种结果，四种动作

发生了什么下一步为什么
测试命令的文件路径拼错局部纠错并重跑计划目标、依赖和完成标准都未变化。
幂等查询超时一次受控重试它可能是暂时故障；必须受预算和幂等性约束。
源码证据推翻“密码校验有问题”的假设revise_plan原修复步骤的前提已经不成立。
权限拒绝或预算耗尽BLOCKED / 停止并报告改计划不能获得权限，也不能制造预算。

修订请求不能只说“换个方案”

RevisionRequest {
expectedVersion: 1,
reason: "源码证据表明过期判断截断到日期，而非密码校验",
evidenceIds: ["ev-3"],
replace: "modifyPasswordLogic" → "fixExpiryCheck"
}

reason 说明为什么旧路径失效，evidenceIds 防止模型凭空换方向，expectedVersion 防止基于旧快照覆盖其他更新。完整字段见 计划修订协议速查。

替换步骤必须原子化

假设原计划是：

s1 reproduce → s2 modifyPasswordLogic → s3 verifyRegression

证据显示根因在过期判断后，正确修订不是删除 s2 再“希望 s3 能继续”，而是一次提交完成：

s2 → SKIPPED（保留历史与原因）
新增 s2b fixExpiryCheck，dependsOn = [s1]
s3.dependsOn: [s2] → [s2b]
记录 replace 与 rewire
全部校验通过后才将 Plan version: 1 → 2

若中间任一步提交，系统可能看到“旧步骤已经跳过、新步骤却尚未接上”，从而错误地判定验证步骤就绪。

候选副本：先验证整体，再改变真相

public Plan revise(RevisionRequest request) {
requireVersion(request.getExpectedVersion());
requireEvidence(request.getEvidenceIds());
Plan candidate = copyOf(currentPlan);
applyChanges(candidate, request);
validateUniqueIds(candidate); validateDependencies(candidate);
validateAcyclic(candidate); validateRevisionBudget(candidate);
return commit(candidate);
}

“候选副本”是原子性的关键：有环、重复 ID、缺失依赖或超预算时，返回错误，原计划一个字段都不变。

修订可改路径，不能改完成定义

可以

替换实现路径

从修密码校验改为修到期时刻判断；下游依赖随之改接。

不可以

降低交付标准

不能把“回归测试通过”改成“尝试运行过”，也不能删测试让任务看起来完成。

用户新增约束时，旧测试也不能自动证明新约束满足：需要检查既有 diff，并做相关的重新验证。

检索练习：该重试、修订还是拒绝？

1. 测试命令的文件路径拼错，正确处置是？

2. 用户新增“不得修改公共 API”，而当前计划包含接口变更，应当？

3. revise_plan 携带 expectedVersion=1，但当前 Plan version=2，应当？

带走的一句话

修订是“带证据的、基于当前版本的、整体校验后提交”的路径调整；它绝不是失败时偷偷降低标准的出口。
