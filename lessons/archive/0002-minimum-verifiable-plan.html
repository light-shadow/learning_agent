Lesson 0002 · 约 15 分钟

把“计划”变成可拒绝错误操作的程序

本课胜利条件：你能为 Coding Agent 画出最小数据模型，并解释为何“模型说完成”不算完成。

设计原则：完成标准在行动前定义，证据在行动后由 Runtime 写入。两者必须分开保存。这样模型即使知道标准，也不能伪造“已完成”。课程讲义 P14-P16

最小模型：四类对象，两个时间方向

行动前

Plan + PlanStep

说明目标、约束、依赖，以及每步结束后应产生什么事实。

行动后

Evidence

记录一次真实工具执行的结果：谁产生、属于哪一步、在哪个代码版本产生。

步骤级

Step Verifier

检查当前步骤引用的证据是否满足它事先写下的 successCriteria。

任务级

Completion Contract

检查整个交付是否齐全，例如变更、三类测试和说明文档。

Java 8 的最小接口

enum StepStatus { PENDING, IN_PROGRESS, COMPLETED, BLOCKED, SKIPPED, FAILED }

class PlanStep {
String id; String objective; List<String> dependsOn;
List<String> successCriteria; StepStatus status; List<String> evidenceIds;
}

class Evidence {
String id; String stepId; String toolCallId; long artifactVersion;
EvidenceKind kind; Map<String, Object> payload;
}

interface CompletionContract {
CompletionResult verify(CompletionContext context);
}

完整字段含义见 最小可验证计划模板。这里最重要的不是字段数量，而是两条边界：

  1. 模型可提议，程序可拒绝。模型提交 complete(stepId, evidenceIds) 只是申请；PlanStore 才能改变状态。
  2. 证据必须绑定版本。修改源码后，先前“测试通过”的证据不自动适用于新代码。

一步完成时，程序应检查什么？

complete(s5, [e4, e5, e6])
→ 证据列表非空？
→ 每项证据存在且属于 s5？
→ test / diff 的 artifactVersion = 当前代码版本？
→ StepVerifier 满足 s5.successCriteria？
→ 才将 s5.status 置为 COMPLETED

这些检查必须在 Runtime 真正执行完工具之后、模型宣称完成之前进行。否则计划只是提示词中的一段文字。

案例：会话过期边界修复

步骤完成标准有效证据
s2：复现失败target 测试 exit code = 1，保存期望与实际断言v0 的测试失败日志
s3：确认根因指出具体实现缺陷，且来自源码读取v0 的源码检查结果
s4：最小修复允许范围内出现受控 diffv1 的 diff
s5：分层验证target / boundary / regression 均 exit code = 0v1 的三份测试结果

注意 s2 的 exit code = 1 只能是复现证据的一部分：它还必须是 target 范围的执行结果，并携带期望值、实际值和断言位置，才能证明“原问题被复现”而非环境或命令失败。证据的意义由步骤标准决定，不能只看退出码正负。

为什么还要 Completion Contract？

每个步骤都完成，只说明局部事实成立；任务仍可能不该交付。例如遗漏交付说明、代码不在当前允许范围，或测试证据不是当前版本。

任务完成 = 当前版本存在允许的改动
AND target / boundary / regression 均通过
AND 交付说明存在且披露未验证项

面试里可以这样说：“我将 StepVerifier 设计为局部正确性检查，将 Completion Contract 设计为任务级合取条件，避免局部通过被误判为可交付。”

检索练习：用规则判断

1. 当前代码版本 v2，s5 引用的通过测试来自 v1，应当？

2. s2 只拿到 exit code 1，缺少断言详情，应当？

3. 模型说“已修复”，但没有引用 evidenceIds，应当？

带走的一句话

Plan 定义要证明什么，Evidence 记录实际证明了什么，Completion Contract 决定这些局部事实是否足以交付。
