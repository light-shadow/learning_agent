何时给 Coding Agent 加显式计划

这节课的胜利条件：面对一个任务，你能在一分钟内选对执行结构，并用一句系统设计语言说明理由。

先记住：Planning 不是“要求模型想得更仔细”。它是让系统保存并检查：为哪个子目标行动、哪些前置已满足、什么证据足以交付。课程讲义 P04、P07

关键边界：Loop ≠ Planning

Loop

回答“下一轮怎么办？”

将工具结果写回上下文，模型据此决定下一轮调用。

Planning

回答“任务还差什么？”

保存步骤、依赖、证据和完成标准，并由程序检查状态转换。

因此，长程修复任务不是因为“模型会依据测试失败调整”就必然需要计划；只有当系统必须持续回答做到哪一步、哪些验证仍欠缺、能否交付时，才加计划层。

把模糊动作改成工程事实

动作：跑测试 → 子目标：target / boundary / regression 三个范围均以 exit code 0 在当前代码版本通过

左边记录“做过什么”，右边规定“完成后新出现了什么事实，以及用什么证据证明”。这正是面试中把“我会拆任务”讲具体的分界线。详见 术语速查。

编码例子：会话过期边界修复

任务包含定位、复现、确认根因、最小修复、三层测试和交付文档；根因开始时未知，且最终交付取决于多个验证结果。因此选择 Agent Loop + 显式计划。

  1. 确认登录入口、会话实现和允许改动范围。
  2. 复现目标用例失败，并保存失败断言。
  3. 用源码证据确认根因，而不是把猜测当结论。
  4. 产生当前版本上的受控最小 diff。
  5. 收集 target、boundary、regression 三类测试通过证据。
  6. 写交付说明，并披露未验证项。

注意：这不是线性待办清单。第 5 步依赖第 4 步，而任何旧版本的测试通过结果都不能证明修复后的代码可交付。

面试的 20 秒回答模板

先按任务不确定性与验收复杂度选执行结构。
当下一步依赖实时结果，用 Agent Loop；当还要持续管理多个子目标、依赖和完成条件，在 Loop 外加入显式计划。
模型只提出动作，PlanStore / Verifier 负责准入和验收，工具结果成为带版本的证据。

检索练习：先选，再看反馈

1. 修复会话过期边界，要求目标/边界/回归测试和修复说明都齐全，应选？

2. 当前版本的目标测试通过，但边界和回归尚未运行，可以交付吗？

3. 测试命令里的文件路径拼错了，优先采取？

带走的一句话

模型负责提出候选行动；系统负责决定是否允许行动、何时算完成。下一课将把这句话落为 Plan、PlanStep、Evidence 和 Completion Contract 的最小数据模型。
