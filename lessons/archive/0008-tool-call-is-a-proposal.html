Lesson 0008 · Function Calling

Tool Call 是提议，不是执行许可

你已经会用 PlanStore 阻止“没有证据就完成”。现在要给真实动作加同样的硬边界：模型说“取消订单”，不等于订单已被取消。

本课的可迁移能力：面对任何 Function Calling 代码，你能指出谁拥有执行权，并写出一条“拒绝时 handler = 0”的验收测试。

从一个危险的直觉开始

用户说：“取消 ord_123。”模型返回：

{ id: "call_7", name: "cancel_order", arguments: { order_id: "ord_123" } }

这是一份候选动作，和用户输入一样不可信。它只回答“模型建议做什么”，没有回答“谁在取消”“是否有权限”“是否已审批”“这次超时后能否重试”。

正确的执行闭环

LLM 产生 call_7
→ Runtime：工具存在？参数有效？可信 userId 有 order:cancel？审批通过？
→ 仅门禁通过才调用 handler
→ Runtime：校验输出，生成带 call_7 的 Tool Result
→ Loop 把 Result 回给 LLM，再决定下一步

这和你的完成契约很像：模型能提出“我完成了”，但不能自己把任务状态改为完成；模型也能提出 Tool Call，但不能自己触发副作用。

可信数据从哪里来？

模型可填

业务参数

order_id、状态筛选、日期。这些仍要经过 Input Schema 和业务规则校验。

Runtime 注入

执行身份与治理

userId、tenant、role、approved、Trace ID。它们来自登录态/审批系统，绝不能放进模型的 Input Schema。

因此，模型可见的是公开的名称、描述和 Input Schema；handler、内部依赖、权限策略属于 Runtime 的私有执行侧。

两个验收不变量

不变量为什么可证明的测试
拒绝发生在 handler 之前参数错误、越权或缺审批不能产生真实副作用。伪造越权 Tool Call；断言结果为 PERMISSION_DENIED 且 handler 调用次数为 0。
结果保留原 tool_call_id并发时完成顺序会变，不能用工具名或顺序配对。让 call_A / call_B 的同名查询乱序结束；断言每个 Result 的 ID 与原调用相同。

不要把“重试”当作安全按钮

查询订单超时，通常可在有限预算内重试：它是只读操作。取消订单超时，则可能已经成功，只是客户端没有收到结果；Runtime 不能直接再取消一次。此时应查询状态、使用幂等键，或转为人工/业务确认。

检索练习

1. AI 给 cancel_order 的 Input Schema 新增 role: admin 与 approved: true。应当？

2. call_A 查询 ord_123，call_B 查询 ord_456。后者先结束。ord_456 的 Result ID 是？

3. cancel_order 超时。Runtime 的安全下一步是？
