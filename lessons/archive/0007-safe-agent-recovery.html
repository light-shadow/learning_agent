让 Agent 中断后安全续跑

本课胜利条件：面对一次中断，你能判断 Agent 应当续跑、等待人工核查，还是明确拒绝恢复。

核心误区：--continue 能让 Agent 记住对话，不代表它知道文件是否已被写入、测试是否真正结束、上次批准是否仍有效。可靠恢复必须先核对现场。课程讲义 P1-P5

先建立正确的心智模型

模型上下文

会话续接

让模型读回消息链，知道此前讨论和工具结果。它解决“模型记不记得”。

业务事实

任务恢复

用状态、步骤记录和 Checkpoint 核对现场，决定是否允许下一次工具调用。它解决“程序敢不敢继续”。

这不是重复存储：前者用于理解上下文，后者用于实施工程规则。比如模型说“补丁还没执行”，但磁盘上的文件可能已经改了。

状态机只管阶段，不替你证明完成

状态含义不能推断什么
running正在分析或决定下一步。不等于没有工具在执行。
waiting_tool已经发起工具调用，等待结果。不等于结果最终可用。
tool_failed一次工具调用失败。不等于整个任务 failed。
waiting_approval具体写操作尚未获批。不等于 cancelled，更不能提前写入。
completed完成契约已被满足。不能只因 agent_end 或一次工具成功就进入。

把“任务阶段”和“停止原因”分开：被 INTERRUPTED 的 running 任务可能仍可恢复；只有业务规则和现场核对才能决定它是否可继续。

一次真实中断：应该怎么判断？

Checkpoint: code = r0, patch 步骤 = pending
实际工作区: session-policy.ts 已出现补丁内容
退出时机: 写工具返回后、下一份 Checkpoint 保存前

这是结果不明，而不是“可以再执行一次补丁”。正确动作是：记录版本差异，停止自动推进，要求核查已写入内容、测试影响或人工决定。这样才不会重复修改、拿旧测试证据冒充新版本验证。

Checkpoint 的恢复顺序

校验存档 → 核对工作区与结果不明操作 → 检查终态/审批/预算
→ 还原计划、步骤记录、证据和计数 → 调用 Agent Loop 续跑

Checkpoint 应在完整轮次结束后保存，并在进入审批前保存具体待批准动作。保存本身应采用“先临时写入、再替换正式存档”，有格式版本和完整性校验；保存失败就停止推进，保留最近有效存档。

审批不是一条布尔开关

对于 Java/Spring 登录过期边界修复，apply_patch 前应先持久化完整补丁并迁移到 waiting_approval。批准时重新比较补丁参数和关联文件摘要：二者任一变化，旧批准失效，必须再次批准。拒绝则不执行，重启也不能默认把“曾经批准”视为有效。

面试收口

“我不会把 Session 当作 Checkpoint。
Session 恢复模型上下文；Checkpoint 恢复可验证的业务状态。
恢复前先校验存档和工作区，结果不明的写操作不自动重放；
写操作经过绑定具体参数的审批门禁，任务完成则必须有当前版本的验证证据。”

本节收束

可靠恢复的顺序始终是：先检查，再恢复；结果不明，先查再做；未经批准，不执行修改；宣布完成，必须有证据。
