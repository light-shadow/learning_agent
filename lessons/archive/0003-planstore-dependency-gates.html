Lesson 0003 · 约 15 分钟

PlanStore：让未就绪动作根本无法执行

本课胜利条件：你能解释为什么状态不能由模型直接改写，并设计一个让 handler 调用次数为 0 的工具门禁。

本课的核心断言：“模型说它遵守依赖”不是证据。只有在 Runtime 调用前由程序拒绝未就绪步骤，依赖才是硬约束。课程讲义 P18、P26-P31

谁有权改变状态？

模型

提出意图

“开始 s4”“完成 s5，引用 e4/e5/e6”“修订计划”。这些都只是请求。

PlanStore

执行规则

检查依赖、合法状态转换、证据和版本；只有它能提交状态变化。

Runtime

执行真实动作

读取代码、写入 diff、运行测试；它产出结构化事实，而非自己判定任务完成。

Verifier

判断充分性

验证 Evidence 是否满足当前步骤标准，以及整个任务是否符合完成契约。

状态机的最小规则

PENDING --(依赖全部 COMPLETED)--> IN_PROGRESS
IN_PROGRESS --(证据充分)--> COMPLETED
IN_PROGRESS --(真实阻塞)--> BLOCKED
IN_PROGRESS --(真实失败)--> FAILED

SKIPPED 不等于 COMPLETED：下游步骤若依赖被跳过的步骤，仍不能开始。必须先修订计划，把下游依赖原子地改接到替代步骤。

Java 8 风格：只暴露受控操作

public void start(String stepId) {
PlanStep step = requireStep(stepId);
if (step.getStatus() != PENDING || !allDependenciesCompleted(step)) {
throw new PlanException("PLAN_STEP_NOT_READY");
}
step.setStatus(IN_PROGRESS);
}

public void complete(String stepId, List<String> evidenceIds) {
requireInProgress(stepId);
evidenceVerifier.verify(stepId, evidenceIds, currentCodeVersion());
requireStep(stepId).setStatus(COMPLETED);
}

这不是完整实现；它刻意省略模型的“聪明”。真正重要的是：没有通过方法校验，就没有状态变化。完整规则见 PlanStore 状态转换速查。

把门禁接入 Agent Loop

一轮开始 → prepareNextTurn：刷新计划快照
模型返回 Tool Call → beforeToolCall：检查 planStepId 与步骤就绪性
通过 → Runtime 执行（先剥离 planStepId）
拒绝 → 写回错误 Tool Result，handler 调用次数 = 0
执行结束 → afterToolCall：补全 stepId / toolCallId / 代码版本，写入 Evidence

这里的 planStepId 是编排元数据，不属于业务工具参数。例如 run_test 最终收到的是测试范围，而不是计划步骤 ID。

为什么“handler 调用次数 = 0”这么重要？

如果先执行测试、写文件或改代码，再事后发现步骤未就绪，约束已失效，副作用也可能无法撤销。真正的验收不是“错误被记录了”，而是错误动作从未触达 Runtime。

在面试中可以这样表达：“我将计划校验放在 beforeToolCall，失败时构造 Tool Result 回写给模型，但不进入业务 handler；因此依赖检查是执行许可而非提示词约定。”

检索练习：判断门禁结果

1. s3 依赖 s2，但 s2 状态是 SKIPPED；模型申请 start(s3)，应当？

2. run_test 是受约束工具，但调用缺少 planStepId，应当？

3. beforeToolCall 校验 planStepId 通过后，传入 Runtime 前应当？

带走的一句话

PlanStore 是计划状态的唯一真相源；beforeToolCall 是行动许可点；afterToolCall 是证据入库点。
