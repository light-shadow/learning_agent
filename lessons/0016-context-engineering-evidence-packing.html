Context Engineering：为本轮判断装配证据

Prompt 是 Context 中的指令部分；Context Engineering 决定模型本轮真正看见哪些规则、代码、工具结果和任务事实。

先装“判断必需品”

本轮 Context = 稳定规则 + 用户约束 + 当前任务状态 + 当前版本证据 + 成对的 Tool Call/Result + 本轮工具快照

以 Spring 登录会话修复为例，模型至少要看到：到期规则、禁止修改既有测试的约束、当前代码片段、失败断言、受测版本与完整日志引用。完整日志不必全部塞进请求，应外存并按需用受控工具读取。

优先级不是“最新优先”

优先保留可压缩或按需读取
用户约束、当前源码、当前失败证据、完成缺项较早探索、重复启动日志、与本轮无关材料
工具调用与其原结果的配对关系完整日志正文，但须保留路径、关键字段与省略数量
影响决策的范围、否定条件与版本不再适用的旧结论，除非用于历史排查

选择依据依次是有效性、当前相关性和遗漏风险，不是消息的时间顺序。

先算预算，溢出就停止

输入预算 = Context Window − 输出预留 − 安全余量

系统提示、工具 Schema、消息、工具参数都占输入空间。发送前做本地估算，发送后用 Provider usage 校准估算与余量；两者口径不同，不能套固定差值。必要项压缩后仍超限时，应缩小代码范围、拆步骤或拒绝发送，不能丢掉关键规则后“碰碰运气”。

压缩保留事实，不制造结论

测试结果至少留下：状态、失败用例、输入/期望/实际、受测版本、异常、完整输出位置和省略量。任务摘要可说明“尚未应用补丁”，但不能把拟议修复写成已经完成。旧测试、冲突来源和外部文本都需标注性质与来源；外部文档仍是数据，不是可提升权限的指令。

1. 预算不足时，应优先保留当前失败证据还是较早探索？

2. 必要规则和证据压缩后仍放不下时，应发送还是停止？
